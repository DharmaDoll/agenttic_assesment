# A案：Strix PoCの実行計画

更新日：2026-11-08。文書作成のみ。導入・診断・実機検証は未実施。

目的は、AIエージェントを使う攻撃者より早く自社の脆弱性を検知すること。まず手動で動かし、結果から次に変える1点を選ぶ。本書は目的・試行順・完了条件を管理し、モデル・導入・Skill・対象環境・操作・出力契約は[実行設計](spec.md)を正とする。設計内容は本書へ重複記載しない。

共通方針は[導入提案](../agentic-security-plan.md)、採用理由は[構成判断記録](../assessment-architecture-decisions.md)に残す。一般的なLinux VM・Docker・モデルAPIは利用できる前提とし、自社のURL・基盤事業者・アカウント・予算額は今は決めない。実行直前に必要値を埋める。

初回は自分たちで起動するJuice Shop。API検査を補う必要があればcrAPI、個別の攻撃検証が止まる場合はDVWAで切り分ける。初回から全環境は作らない。やられサイトでの検証後、自社検証環境へ段階的に進む。

## 1. 最初の一周

最初の成果は「agentが限定対象へアクセスして探索し、操作と観測の証拠を保存できた」という実測。候補を人が再現し、未確認範囲を整理して、次に試すことを1つ決める。検出0件でも試行結果にはなるが、安全性や検出能力の証明にはしない。

| 作業 | 今回やること | 終わったと判断する証拠 |
|---|---|---|
| P0：対象と入力 | Juice Shopの限定環境、選定モデル、入力資料を準備する | 実行設計第3節の実行メモ |
| P1：動く入口 | Strixの版を固定し、help・モデル接続・資料受渡しを確認 | 実際の起動コマンド、SHA・image digest・モデルID、接続結果 |
| P2：短い接続・停止試験 | 対象到達、対象外遮断、正常終了・キャンセル・期限停止を試す | 外側の通信ログ、停止状態、途中出力 |
| P3：探索1回 | 実行設計第4節の入力で探索し、native出力を保存する | 対象側の操作記録とagentの観測。失敗も原因を保存 |
| P4：結果を見る | 候補を独立再現し、確認表と次の判断を記入する | 実行設計第6節の結果と構成判断記録 |

P0→P1→P2→P3→P4で一周する。既存環境とモデルアクセスがあれば最初の結果まで半日〜1日を目安とする。これは検査完了の期限ではない。P1の調査が半日を超えそうなら障害を絞り、構成を見直す。独自runner、DB、UI、スケジューラ、比較基盤の完成を待たない。

各周回で「分かったこと／まだ分からないこと／次に変える1点」を残す。認証失敗なら認証、資料不足なら資料を直して次の枠で試す。モデルやSkillも必要に応じて一要因ずつ試す。モデルの組合せを網羅的に比較するより、対象に該当する脆弱性領域を広く確認する。再試行・比較は合意した1日1枠と総予算に含め、自動再試行・自動提供者切替はしない。

## 2. 一周の確認と次の判断

各項目に `PASS / FAIL / BLOCKED / NOT RUN` と証拠を付ける。現時点はすべてNOT RUN。

| 確認 | 判定内容 |
|---|---|
| 実行前提 | 対象・権限・予算・版・入力・担当が確定。不足時に起動しない |
| 起動と停止 | 対象への実操作、モデルと資料の利用、対象外遮断と全worker停止の証拠 |
| 探索と保存 | 行動・観測・次の判断、native証拠、終了状態を辿れる |
| 検査範囲 | 全領域に証拠、該当なし根拠、または未確認理由と次の検査がある |
| 候補評価 | 独立再現と未判定を区別。候補0件なら再現評価は該当なし、検出力は未判定 |
| 次の一手 | 時間・費用・介入・残る侵害可能性を記録し、次に試す1点を選んだ |

起動成功、侵害可能性の評価完了、継続採用は別判定。短い試行が終わっても未確認領域の検査は継続する。選択理由は[構成判断記録](../assessment-architecture-decisions.md)へrun ID、agentの役割、モデル・入力、結果・制約、次の最小作業と再検討条件を残す。

## 3. 必要になってから選ぶバックログ

旧A00〜A12を以下へ集約する。全件を順番に実装する約束ではない。具体的な構成・操作・出力は実行設計だけで管理し、第三の設計書は増やさない。

| 着手のきっかけ | 次の成果・確認 | 旧ID |
|---|---|---|
| 初回の障害が分かった | 対象・入力・版・境界・fixtureの不足だけ補い、P0〜P2の証拠を再利用 | A00〜A04 |
| 手動反復が負担 | 小さなrunner：入力検証、排他、固定引数、起動前記録、証拠保存。shell評価なし | A05 |
| 自動停止・回収が必要 | 全worker合算の期限・流量制限、残存回収。強制終了・host再起動・出力破損・容量不足でも未完了記録 | A06 |
| 結果整理が負担 | 原証拠に対応するfinding・確認済み要約。古いrevisionの検査済みを転用しない | A07 |
| 検出能力の継続判断 | 欠陥版・修正版をresetし各3回以上。正解を隠し正常操作・既存診断も比較、失敗も分母へ | A08 |
| 自社実対象へ拡張 | 通常の外部経路、操作・復元・予算で手動確認。制御不合格なら拡張しない | A09 |
| 日次実行が有用 | 既存スケジューラ、timezone、1日1枠、重複拒否、欠測確認、自動埋め合わせなし | A10 |
| 継続性を測る | 10日次枠、変更・未探索・確認済み要約の引継ぎ、重大候補の当日確認、修正の次回再検証 | A11 |
| 採用を判断 | 検知遅延、追加検出、人手、費用、未確認範囲から継続・改善・他案を選ぶ | A12 |

自動化を選んだ時点で、その小部分の引数・保存項目の型と必須条件・状態遷移・異常時テスト例を実行設計へ追記して実装する。コードは `src/assessment_runner/`、テストは `tests/assessment_runner/`、非秘密fixtureは `assets/assessment-fixtures/`。偽プロセスによるrunner検証と実Strixの境界・停止・出力確認は分ける。実在するセットアップ・テストコマンドをコード追加時にREADMEへ載せる。

継続評価では公開／変更から確認済みfindingまでを、日次枠待ち・探索・独立確認に分ける。起点不明なら初回観測と明記する。検出率80%以上・重大ケース全件・誤判定10%以下・重要経路90%以上は導入提案の後段仮目標。分母と判定者を評価前に固定し、初回起動の条件にはしない。未完了・欠測も報告する。

状態を持つフロー不足ならB、日次選択・引継ぎ負荷ならC、証拠管理負荷ならDを再検討する。未試行の案の性能や攻撃者の能力上限は断定しない。
